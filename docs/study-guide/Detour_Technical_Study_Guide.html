The three unit traps
  • Sun avoidance is 0–100 in the UI and in the URL (sun_avoidance=50); the backend divides by 100 and works with 0.5.
  • Sun % (sun_percent) is already a percentage when it leaves the backend (e.g. 95.1), not a fraction.
  • Cloud cover is a fraction 0–1 in the API (0.7) and the UI multiplies it by 100 to show "Cloud 70 %".
The coordinate trap

The frontend and Leaflet use [latitude, longitude]. GeoJSON uses [longitude, latitude]. The backend computes in metres (UTM zone 17N: x = east, y = north). See §4.4.

1Project overview

Detour finds walking routes across York University's Keele Campus that keep you out of the direct sun (and, optionally, out of the rain), and shows how much extra walking that costs.

1.1 The problem

Normal navigation apps minimise time or distance. On a hot day, the fastest route can be in full sun while a route that is only a minute longer runs along the shady side of buildings and trees. Detour answers: "How much sun can I avoid, and what does it cost me in time?"

1.2 What the user does

  1. Clicks the map to place a start pin and an end pin (only inside the campus outline).
  2. Chooses a date and time (defaults to "now" in Toronto) and a sun avoidance level from 0 % to 100 %.
  3. Optionally turns on Avoid rain and Show shadows.
  4. Sees two routes: the Fastest route (dotted red) and the Detour route (solid green), with time, distance and sun % for each, plus the live weather used.

2.3 CampusMapLoader.tsx: why the map is loaded dynamically

"use client";
const CampusMap = dynamic(() => import("./CampusMap"), {
  ssr: false,
  loading: () => <div aria-label="Loading map" className="campus-map" />,
});
Why ssr: false

Leaflet reads window and document as soon as it is imported. On the server those do not exist, so importing Leaflet during server rendering would crash. dynamic(..., {ssr:false}) means: render an empty placeholder on the server, then download and run CampusMap only in the browser. In Next.js 16 ssr:false is only allowed inside a client component, which is why this tiny wrapper file exists.

2.4 CampusMap.tsx: the main component

About 500 lines. It owns all the state, calls the backend through the useRemote hook, draws the Leaflet layers and renders the side panel (sections 01 Route, 02 Trip, 03 Environment).

2.5 PanelControls.tsx

Presentation-only components; no routing logic.

  • Slider: a controlled <input type="range"> with a label and a formatted value. Its CSS variable --fill = (value − min)/(max − min) × 100 % colours the track.
  • Switch: a controlled checkbox with role="switch" (accessible toggle).
  • RoutePair / RouteSummary: Detour and Fastest side by side: time (fmtSpan: "1 min 19 sec"), distance (fmtDistance: "427 m" or "1.65 km"), sun %, and rain % only while it is raining. The delta line uses the backend's extra_seconds.

2.6 lib/route.ts

Pure helpers with no React and no maths, kept apart from the components: the TypeScript types of the API, constants (campus centre [43.7735, -79.5019], map bounds, DEFAULT_AVOIDANCE = 50, AVOID_RAIN_W = 10, date range 1900–2100), nowInToronto(), routeQuery(), shadowQuery(), the validators parseRoute / parseShadows / parseCampus, the point-in-polygon test insideRing(), and getJson().

Toronto time. nowInToronto() uses Intl.DateTimeFormat with timeZone: "America/Toronto", so the default date and time are Toronto wall-clock time even if the judge's laptop is set to another time zone. For example: 18:07 UTC in June → 14:07 (EDT); 03:03 UTC on 15 Jan → 22:03 on 14 Jan (EST).

Weather and "comfort" files

There are no weather or comfort files in the frontend. The frontend never calls Open-Meteo; it only displays the weather object that the backend includes in each /route response (§11). There is no Smart/Comfort mode in the code (§13).

3Frontend → backend request flow

What happens between "the user moves a slider" and "the green line moves".

3.1 The URL that is actually sent

GET /route?date=2026-06-21&time=14:00&sun_avoidance=50&w_rain=0
          &from_lat=43.7735&from_lon=-79.5019&to_lat=43.779&to_lon=-79.496

routeQuery() sends the slider's 0–100 sun_avoidance as is, sends w_rain=10 when "Avoid rain" is on (else 0), and sends pins as separate lat/lon numbers. Shadows use a different, smaller query (shadowQuery: only date and time), because shadows do not depend on pins, sun avoidance or rain.

3.2 The custom hook useRemote

src/components/CampusMap.tsx

useEffect(() => {
  if (!path) return;                       // null path = don't fetch (e.g. pins not placed)
  const controller = new AbortController();
  const timer = setTimeout(async () => {   // debounce: wait 150 ms
    try {
      const value = parse(await getJson(path, controller.signal));
      if (controller.signal.aborted) return;
      setLoaded({ path, value });          // remember WHICH path this answer belongs to
      setError(null);
    } catch (e) {
      if (controller.signal.aborted) return;
      setError({ path, message: e instanceof Error ? e.message : String(e) });
    }
  }, 150);
  return () => { clearTimeout(timer); controller.abort(); };   // cleanup
}, [path, parse, attempt]);

Debounce (150 ms)

Dragging the time slider from 14:00 to 14:20 changes state 20 times. Each change re-runs the effect, whose cleanup cancels the previous timer. Only when the slider rests for 150 ms does a request go out. Result: one request instead of twenty.

AbortController

If a request is already in flight and the path changes, the cleanup calls controller.abort(). The browser cancels the HTTP request, and the aborted checks guarantee an old answer can never overwrite a newer one (no race condition).

Stale routes

stale = loaded.path !== path. While a new answer is loading, the old route stays on the map but is dimmed (lower opacity, Detour dashed "6 8") and the panel says "Updating...". The user never sees an empty map flash.

Retry

An error is stored with its path, so it only shows while it belongs to the current request. Retry bumps attempt, a dependency of the effect, which re-runs the fetch. After tonight's audit it retries only what failed, including the campus outline (§15).

3.3 API validation: getJson and parseRoute

  • getJson turns failures into human messages: network failure → "can't reach the backend at http://localhost:8000"; HTTP 422/404 → the backend's detail text (e.g. "start is outside York University's Keele Campus"); an abort is re-thrown untouched so the hook can ignore it.
  • parseRoute checks that the JSON really has finite numbers for each route's seconds, distance, sun % and rain %, a geometry object, the extra seconds, the number of options and a known weather source: exactly the fields the UI uses. If not, it throws "unexpected /route response", which is shown as an error instead of crashing the page during rendering. isNum rejects NaN and Infinity.
Likely question

"What happens if the backend is asleep?" The free Render plan sleeps after 15 min; the first request waits about a minute while it wakes. If a request fails, the panel shows the error and a Retry button. The map, pins and controls keep working.

4.1 Leaflet vs OpenStreetMap

OpenStreetMap (OSM)

A free, community-made map database of the world. We use it twice: (1) the background tile images from tile.openstreetmap.org, and (2) the data the backend downloaded once with OSMnx: footpaths, the campus boundary (OSM way 15396822) and tree locations.

A JavaScript library that displays an interactive map in the browser: panning, zooming, tiles, markers, lines and polygons. react-leaflet wraps Leaflet so each map layer is a React component.

4.3 Layer order (what is drawn on top of what)

Route casing (the white outline)

Each route is drawn twice: first a wider white line (the "casing"), then the coloured line on top, so the route stands out over any map colour. Order: fastest casing (white, 8.5 px) → fastest (red #e0161b, 5 px, dotted "1 9") → Detour casing (white, 11 px) → Detour (green #138a3e, 7 px). Detour is drawn last, so it is the "hero" line on top.

Why GeoJSON layers have a key

react-leaflet's <GeoJSON> ignores later changes to its data prop. Each layer's key includes the request path (e.g. key={`ctx-${route.path}`}), so when a new answer arrives React throws the old layer away and creates a new one. Style changes such as stale dimming are still applied through the style prop.

Shadows: drawn only when needed

The shadow request path is null while "Show shadows" is off, so nothing is fetched. When on, the backend sends one MultiPolygon of overlapping pieces (≈1.45 MB at midday); Leaflet draws it with fillRule: "nonzero", which fills overlapping pieces once, so it looks exactly like the merged shadow without the backend having to merge thousands of polygons.

Draggable pins and the campus rule

Pins can only be placed inside the campus polygon. The frontend checks with insideRing() (ray casting: count how many polygon edges a horizontal ray from the point crosses; odd = inside). A pin dragged outside is put back where it was, and a message appears. The backend checks the same polygon again (it never trusts the client) and answers 422 for an off-campus pin. Any pin inside the campus is accepted, however far it is from a path: it snaps to the nearest walkway node and a dotted line joins it to the route.

4.4 Coordinate order: the most common bug in mapping

Where the swaps happen in code: parseCampus maps ([lon, lat]) => [lat, lon]; lineEnds reads [a[1], a[0]]; the Leaflet GeoJSON component reads [lon, lat] itself; the backend's pyproj transformers use always_xy=True (x = longitude first). origin/destination in the response are [lat, lon]. During development a test checked that the first route coordinate has -80 < lon < -79 and 43 < lat < 44.

5Backend: FastAPI and data

5.1 FastAPI in one paragraph

FastAPI turns Python functions into HTTP endpoints. The function's parameters become query parameters, and their types and limits are validated automatically: sun_avoidance: float = Query(50.0, ge=0, le=100) means a request with sun_avoidance=101 is rejected with HTTP 422 before our code runs. Response models (RouteResponse, Pydantic) guarantee the JSON shape. FastAPI also generates interactive docs at /docs.

5.3 Start-up (the lifespan function)

  1. load_campus() reads the cached files in backend/cache/ (no internet needed): the walk graph, 737 building footprints with heights, 1,181 trees and the campus polygon. (If the cache were missing it would download from OSM via Overpass, rotating 3 mirror servers with exponential back-off.)
  2. Builds the base ExposureModel: places 121,632 sample points every 1.5 m along all edges, indexes them in an STRtree, and computes each edge's rain shelter fraction. This is done once.
  3. Indexes the 1,804 graph nodes in a Shapely STRtree (for snapping pins), snaps the demo trip's endpoints and creates empty caches.

Uvicorn only opens the port after this finishes, which is why the frontend can briefly report "can't reach the backend" during start-up (then Retry).

6Graph theory

A map of walkways is a graph. Routing is "find the best path through a graph".

G = (V, E)
TermMeaning in Detour
Vertex (node) v ∈ VA point where walkways meet or end. Has metric coordinates x, y. |V| = 1,804.
Edge e = (u, v) ∈ EA walkway segment from u to v, with a length in metres and its exact curved geometry. |E| = 5,172.
DirectedEach walkway is stored in both directions (u→v and v→u), because shade is computed per edge entered at a time.
MultigraphTwo nodes may be joined by several different walkways (key 0, 1, …). NetworkX MultiDiGraph.

Weight / costA number per edge; the cost of a path is the sum of its edge costs.

Why the graph is projected to metres

OSM stores degrees. One degree of longitude at Toronto is only about 80 km, but one degree of latitude is about 111 km, so distances in degrees are distorted. Projecting to UTM zone 17N (EPSG:32617) makes x and y true metres, so length, straight-line distance and shadow offsets are all directly in metres.

6.1 Snapping a pin to the graph

A clicked point is usually not exactly on a node. _snap() in api.py converts the point to metres, checks it is on campus, and finds the closest node with a Shapely STRtree built once at start-up, however far away that node is. The walk graph is one strongly connected component (every node can reach every other), so any two pins always have a route. The dotted connector lines on the map show the gap between a pin and the node its route starts from.

7Routing mathematics and algorithms

7.1 The edge cost (router.py)

cost(e, t) = τe + wr·We(t)     and, as a separate second criterion, sun Se(t)
SymbolMeaningUnitValue in the app
τe = de / vtime to walk edge e (length de, speed v)secondsv = 1.4 m/s
Se(t)sun exposure on e if entered at time t (§10)sun-secondssecond criterion (§7.4)
We(t)rain exposure on e if entered at time t (§12)rain-secondscomputed
wrseconds of walking traded per rain-seconds / rain-s0, or 10 with "Avoid rain"

Both terms are in seconds, so the weight has a plain meaning: "how many seconds of extra walking would I accept to avoid one second out in moderate rain?" Sun has no weight in the cost: adding ws·Se is the obvious idea, but §7.4 shows why Detour treats sun as a second criterion instead, and §7.6 works through what a sun weight would do.

7.2 Dijkstra's algorithm

Keep a priority queue (a heap) of nodes ordered by the best known cost from the origin. Repeatedly take the cheapest node, mark it settled, and try every outgoing edge: if going through it is cheaper than what a neighbour had, update the neighbour. When the destination is settled, follow the "came from" links backwards to get the path. With non-negative edge costs, the first time a node is settled its cost is optimal.

7.3 A* = Dijkstra + a good guess

A* orders the heap by cost so far + h(n), where h(n) is a lower bound on the remaining cost. Detour uses straight-line walking time:

h(n) = 0.99 · straight-line distance(n, goal)1.4 m/s
  • No walkway can be shorter than the straight line, and every edge costs at least its walking time (the rain term is ≥ 0), so h never overestimates: it is admissible and consistent. A* therefore returns exactly the same route cost as Dijkstra (checked on the real campus during development).
  • The 0.99 "slack" is because OSM edge lengths can be a hair shorter than the projected straight line (measured ratio ≥ 0.9975).
  • Benefit, measured on the demo trip during development (21 June, 14:00): A* settled 876 nodes vs Dijkstra's 1,703, about half the work.

Time-dependence: S and W depend on the time you enter an edge, so each search label carries its arrival time. Settling by accumulated cost is exact only if arriving earlier never makes the rest of the walk costlier; over a walk of minutes the sun barely moves, so the error is negligible (documented assumption).

7.4 How the app really picks the Detour route: the Pareto set

A single weight time + ws·sun only finds routes on the convex hull of the time-vs-sun trade-off, so the route "jumps" as the weight changes and some good compromises are never chosen. So Detour has no sun weight. Instead shade_options() finds the Pareto set: every route that no other route beats on both time and sun.

  • Algorithm: bicriteria label-setting (Martins' algorithm) with A* keys. A node may hold several labels (cost, sun, arrival time). Labels pop in cost order; a new label at a node is kept only if its sun is lower than every label already kept there.
  • Criterion 1: c = τ + wr·W (time, plus rain if Avoid rain is on).
  • Criterion 2: sun-seconds S.
  • Limit 1 (MAX_DETOUR = 0.5): options may cost at most 50 % more than the quickest.
  • Limit 2 (SUN_STEP = 0.02): each new option must cut sun by at least 2 % of the quickest route's sun (and at least 1 sun-second), so near-identical routes aren't counted.

7.5 The slider: pick()

backend/router.py

def pick(options, avoidance):          # avoidance = sun_avoidance / 100, so 0..1
    most, least = options[0].sun_seconds, options[-1].sun_seconds
    target = most - avoidance * (most - least)
    return next(r for r in options if r.sun_seconds <= target + 1e-9)
target = Sfastest − p · (Sfastest − Sshadiest)    then choose the quickest option with S ≤ target

Sun avoidance p means "avoid at least p of the sun that can be avoided on this trip". 0 % = fastest, 100 % = shadiest option. Options are already sorted quickest-first, so the first one that meets the target is the quickest that does.

Likely question

"Why not compute the sun once for the whole route?" The router does use the time each edge is entered, but sun position changes only ~0.25° per minute, so shadows are recomputed every 15 minutes (nearest slice), while sun intensity is interpolated to the second.

9Shadow mathematics

9.1 Shadow length

L = htan(θ)

In plain English: the sun ray from the top of a building of height h hits the ground a distance L away. The ray, the wall and the ground make a right-angled triangle; tan(θ) = opposite / adjacent = h / L, so L = h / tan(θ). The lower the sun, the smaller tan(θ), the longer the shadow.

Two safety rules from shadow.py: below 3° no shadows are computed (tan θ → 0 makes L → ∞ and the model stops being meaningful); every shadow is capped at 300 m.

9.2 Shadow direction

The shadow points away from the sun. With azimuth α measured clockwise from north (x = east, y = north), the ground offset of the roof is:

(Δx, Δy) = ( −L·sin α,  −L·cos α )

Check: sun due south (α = 180°): sin = 0, cos = −1 → (0, +L): shadow points north ✔. Sun in the east (α = 90°): (−L, 0): shadow points west ✔ (both were checked by unit tests during development).

backend/shadow.py (inside ShadowCaster.pieces)

tan_el = math.tan(math.radians(sun.elevation))      # degrees -> radians before tan!
alpha = math.radians(sun.azimuth)
direction = np.array([-math.sin(alpha), -math.cos(alpha)])
high = np.minimum(self._cvx_h / tan_el, MAX_SHADOW_LENGTH_M)   # L = h / tan(theta), capped

9.3 From one point to a whole building

A building is modelled as a prism: its footprint polygon extruded straight up to height h. Its shadow on flat ground is the footprint swept along the offset vector.

  • Convex footprints (area ≥ 98 % of their convex hull, no holes): shadow = convex hull of the footprint and its shifted copy. Computed for all such buildings in one vectorised call.
  • Concave footprints (L, U shapes, courtyards): a hull would wrongly fill the courtyard, so each wall edge sweeps a parallelogram; shadow = footprint + all parallelograms. During development a unit test confirmed that a U-shaped building keeps its sunlit gap.

9.4 Trees

OSM trees have no size data, so every tree gets the same crown: a 12-sided disk of radius 3 m floating from 2 m (canopy base) to 9 m (top); the trunk is ignored. The crown base casts its shadow 2 / tan θ away and the top 9 / tan θ away; the tree's shadow is the convex hull of those two shifted disks. Consequence: the ground directly under a tree is shaded only when the sun is high (checked: shaded at 89°, not at 20°, where the base shadow is 2 / tan 20° ≈ 5.5 m away, beyond the 3 m crown).

9.5 Which walkway parts are in shadow?

Sample points every 1.5 m along each edge (at least 2 per edge; 121,632 in total). For each 15-minute time slice, the shadow pieces are tested against an STRtree of those points. The shade fraction is:

f(e) = number of e's sample points inside any shadownumber of e's sample points

During development a test compared this to exact line-polygon overlap on the whole campus at 9:00, 13:00 and 17:00: the length-weighted difference was under 0.5 percentage points. Walkways inside building footprints count as fully shaded (indoor connections).

10Exposure mathematics and units

10.1 Sun intensity I(t)

I(t) = direct radiation(t)  [W/m²]1000 W/m²    (live weather)     or     I(t) = max(0, sin θ(t))    (clear-sky fallback)

Shade only blocks the direct beam; diffuse skylight reaches you in the shade too. So intensity uses Open-Meteo's direct radiation, not total sunlight. Under full overcast the direct beam is ~0, so there is nothing to avoid, and the Detour and Fastest routes coincide. This is how clouds affect routing: through direct radiation, not through the cloud-cover number.

10.2 Sun-seconds on one edge

Se = ∫tete+τe I(t) · (1 − f) dt  ≈  τe · I(te) + I(te + τe)2 · (1 − f)

A sun-second is one second spent in full-strength direct sun (I = 1, no shade). The integral is approximated with the trapezoid rule (average of the intensity at entry and exit), and f comes from the nearest 15-minute shadow slice.

Worked example

A 14 m edge: τ = 14 / 1.4 = 10 s. Intensity 0.80 at entry, 0.82 at exit, shade f = 0.25.
S = 10 × (0.80 + 0.82)/2 × (1 − 0.25) = 10 × 0.81 × 0.75 = 6.08 sun-seconds.

10.3 Route totals and "Sun %"

T = Σ τe     S(P) = Σ Se     Sopen(P) = Σ Se with f = 0     sun % = 100 × S(P) / Sopen(P)

Each edge is entered at the time you actually reach it (start time + time walked so far). Sun % = the share of the sun this path could give you that it actually gives you. It is about shade, not weather: if intensity is the same everywhere, it cancels, and sun % ≈ the time-weighted share of the walk that is unshaded. At night or under full overcast, Sopen = 0 and sun % is defined as 0.

12Rain

Rain routing is implemented, but it only changes the route when two things are both true: "Avoid rain" is on and the forecast has rain at that time.

Rain displayed
  • Weather line always shows rain … mm/h (live weather).
  • Each route card shows a Rain % row only while it is raining at the departure time (rain_mm_h > 0).
  • The switch caption says "No rain at this time" when the forecast is dry.
Rain affecting routing
  • "Avoid rain" sends w_rain=10 (else 0).
  • The Detour options then use cost c = τ + 10·W.
  • The Fastest route is always pure time; it never avoids rain.
  • No rain in the forecast → W = 0 → no effect.

12.1 Rain maths

R(t) = min(1, rain(t) / 4 mm/h)      We = ∫ R(t) · (1 − g(e)) dt ≈ τe · R(te) + R(te+τe)2 · (1 − g(e))
  • R: rain intensity 0–1; moderate rain (4 mm/h) or heavier counts as 1.
  • g(e): the edge's shelter fraction: share of its 1.5 m sample points inside a building footprint, or 1 if OSM tags it as roofed (covered=yes/arcade/colonnade, indoor=yes/corridor, highway=corridor, tunnel=building_passage/yes). 364 directed edges are more than half sheltered.
  • wr = 10: accept up to 10 s of extra walking per rain-second.
Worked example

Raining 2 mm/h → R = 0.5. Open 30 s edge: W = 30 × 0.5 = 15 rain-s → cost 30 + 10 × 15 = 180. Covered 45 s corridor (g = 1): W = 0 → cost 45. The router takes the corridor.

Limits

Rain is assumed to fall straight down (wind ignored). Indoor connections are assumed open. Rain % in the UI uses the rain at departure time to decide whether to show the row; routing integrates rain along the whole walk.

13Smart / Comfort mode

Not in the code

There is no Smart or Comfort mode in the current code: no heat base, cloud factor, sun factor or comfort score, in either the frontend or the backend. If a judge asks, the honest answer is that "heat-aware" in Detour means direct-sun exposure, measured in sun-seconds from real shadows and live direct radiation; air temperature and humidity are not used. A comfort score combining temperature, humidity and sun would be a natural next step.

16Limitations (honest list)

Physical model

  • Flat ground; constant walking speed 1.4 m/s (no stairs, slopes or crowds). Terrain elevation was removed earlier.
  • "Heat" = direct-sun exposure only. No air temperature, humidity, wind, or heat from pavement.
  • Buildings are prisms at their maximum height (Toronto MAX_HEIGHT), which overestimates shadows of buildings with lower wings.
  • All trees are the same size (3 m crown, 2–9 m high); OSM may miss trees; leaves are assumed present all year.
  • Shadows only from buildings and trees; no awnings, bridges or overhangs (unless tagged covered).
  • No shadows below 3° elevation; length capped at 300 m.
  • Shade sampled every 1.5 m; shadows from the nearest 15-minute slice.
  • Indoor connections assumed open and fully shaded/sheltered at any hour.

Data and weather

  • One weather point for the campus; hourly data interpolated.
  • Weather only for dates Open-Meteo covers; otherwise clear-sky fallback (clearly labelled).
  • DST-change days: weather can be an hour out after 02:00.
  • Rain is vertical; wind-blown rain ignored.

Algorithm

  • Time-dependent search assumes leaving earlier never hurts (negligible error over minutes).
  • Options capped at 50 % extra cost; options must differ by ≥ 2 % of the fastest route's sun. A trip may have only 1–2 options, so the slider can do nothing over a range.

Product and engineering

  • Keele Campus only; pins must be inside the campus. The dotted link from a pin to the nearest path is not counted in the route's time or distance.
  • Free Render plan sleeps after 15 min; first request then waits ~1 min.
  • Single backend process with in-memory caches (cleared wholesale when full).
  • No automated tests in the final repository (they were removed; lint and the type-checked build remain). No mobile GPS / live navigation.

17Judge Q&A

Short, accurate answers. Say "I don't know, but here's how I'd find out" rather than guess.

Frontend and React
Why Next.js and not plain React?
It gives us a build system, TypeScript, optimised fonts and images, and a static prerendered page shell for free. The interactive map is a client component loaded only in the browser.
What is state in your app?
Date, minutes, sun avoidance, avoid rain, the two pins, which pin is being placed, show shadows and the off-campus notice; plus each useRemote's loaded value, error and retry counter. Everything else (request paths, stale flags, formatted numbers) is derived on each render.
Why is the map loaded with dynamic(..., {ssr: false})?
Leaflet uses window at import time, which doesn't exist during server rendering. So the server sends a placeholder and the browser loads the map.
What does useEffect do in useRemote?
It starts a 150 ms timer and then fetches. Its cleanup clears the timer and aborts the request, so every change of the request path cancels the previous one.
How do you stop an old response overwriting a new one?
Each request has an AbortController that is aborted when the path changes, and the code checks signal.aborted before setting state. Results are also stored with the path they belong to.
What is a controlled input?
An input whose value comes from React state and whose onChange updates that state, like our sliders, date picker and switches. React state is the single source of truth.
How do you validate the API response?
parseRoute checks the type of every field the UI uses (finite numbers, geometry object, known weather source) and throws a clear error otherwise. During development it was tested with malformed responses.
Leaflet and mapping
What is the difference between Leaflet and OpenStreetMap?
OSM is the data (and free tile images); Leaflet is the JavaScript library that shows an interactive map in the browser.
Why are coordinates sometimes [lat, lon] and sometimes [lon, lat]?
Leaflet uses [lat, lon]; the GeoJSON standard uses [lon, lat] (x before y). We convert in parseCampus and lineEnds, and during development a backend test checked the GeoJSON order.
How do you make sure shadows don't cover the route?
Shadows live in a custom Leaflet pane with z-index 350, below the overlay pane (400) where routes are drawn, and above the campus mask pane (340).
Why does the route have a white border?
It is a "casing": a wider white line drawn underneath so the coloured route is readable over any map background.
Why do GeoJSON layers have a key?
react-leaflet's GeoJSON ignores changes to its data, so we key it by the request path; a new response creates a new layer.
Backend
Why a separate Python backend?
The geometry, astronomy and graph libraries we need (Shapely, pvlib, OSMnx, NetworkX) are Python. The frontend only sends settings and draws results.
What does FastAPI validate for you?
Types and ranges of every query parameter (e.g. sun_avoidance 0–100, w_rain 0–50, valid date/time), answering 422 automatically. We add checks for the date range and the campus boundary.
Why is moving the sun-avoidance slider so fast?
The whole set of route options is cached per trip, time and rain weight; the slider only re-runs pick() on the cached list. A cached request takes about 15 ms on the server.
How does the backend know a pin is on campus?
It converts the pin to metres and tests it against the OSM campus polygon with Shapely, then snaps it to the nearest graph node, however far away it is. The frontend does the same polygon check first (ray casting), but the backend never trusts the client.
Does the app need the internet to compute routes?
Only for weather and map tiles. The graph, buildings and trees are committed cache files loaded at start-up; without weather it falls back to a clear sky.
Graphs and algorithms
What are the vertices and edges?
Vertices are walkway intersections/endpoints (1,804); edges are walkway segments in each direction (5,172) with length and geometry, from OpenStreetMap.
Dijkstra or A*?
A*, which is Dijkstra plus a lower-bound estimate of the remaining cost. Our estimate is straight-line distance ÷ 1.4 m/s × 0.99. It never overestimates, so A* returns the same optimal cost as Dijkstra (checked during development) while settling about half as many nodes (876 vs 1,703 on the demo trip).
Why is your heuristic admissible?
No path is shorter than the straight line, and every edge costs at least its walking time because the rain term is never negative.
Why not just add sun to the cost with a weight?
A weighted sum can only find routes on the convex hull of the time/sun trade-off, so the route jumps and skips good compromises. We compute the full Pareto set and let the slider choose among all of them.
What is a Pareto-optimal route?
One that no other route beats on both time and sun at once. Every option in our list is slower but shadier than the one before.
What does 50 % sun avoidance mean exactly?
Take the quickest route that removes at least half of the sun that is avoidable on this trip (the difference between the fastest and the shadiest option).
What's the complexity?
A* with a binary heap is O(E log V) in the worst case. The Pareto search can hold several labels per node, so it is bounded by limiting options to 50 % extra cost and requiring each to cut sun by 2 %; in practice the first request for a trip takes about 0.25 s and later ones are cached.
Mathematics
How do you compute a shadow?
L = h / tan(θ): a roof at height h casts its shadow L metres away, opposite the sun: offset (−L sin α, −L cos α). The building's shadow is its footprint swept along that offset (convex hull for convex buildings, per-wall parallelograms for concave ones).
What is a sun-second?
One second spent in full-strength direct sun. Half-strength sun for two seconds is also one sun-second. Per edge: walking time × average intensity × unshaded fraction.
What does "Sun 27 %" mean on the card?
The route gets 27 % of the direct sun it would get if nothing cast a shadow on it. The backend sends 27.x, already a percentage.
Why the trapezoid rule?
Sun intensity changes over a walk, so exposure is an integral over time. The trapezoid rule averages entry and exit intensity per edge; edges take seconds, so it is very accurate.
Degrees or radians?
The API and UI use degrees; the code converts with math.radians before sin/tan.
How accurate is the 1.5 m sampling?
During development a test compared it with exact line/polygon overlap over the whole campus at three times of day; the length-weighted difference was under 0.5 percentage points.
Weather and rain
Where does the weather come from and how often?
Open-Meteo, hourly direct radiation, cloud cover and precipitation, fetched by the backend and cached 30 minutes per date (60 s after a failure).
Do clouds change the route?
Yes, through direct radiation: under heavy cloud the direct beam is weak, so there is little sun to avoid. The cloud-cover percentage itself is only displayed.
Is rain routing real?
Yes. With "Avoid rain" on, the Detour cost becomes time + 10 × rain-seconds, where rain-seconds count rain intensity on unsheltered walkway (buildings and OSM covered/indoor tags give shelter). If it isn't raining, it changes nothing.
What if the weather API is down?
The backend falls back to a clear, dry sky (sun intensity = sin of elevation) and the panel says "Weather unavailable, assuming clear sky".
Design, testing, limitations
Why show the fastest route too?
So the user sees the trade-off: "+48 sec vs fastest" and "Sun 89 % → 71 %". Detour is green and drawn on top; Fastest is a red dotted reference.
How do you know the router is correct?
During development, automated tests checked that the fastest route matches NetworkX's shortest path on random campus pairs, that A* matches Dijkstra, that the Pareto options are strictly slower and shadier and include every weighted-sum route, and that a toy graph with a known answer takes the shade detour. They all passed on the final code before the test files were removed.
Do you have automated tests?
We wrote 75: 15 frontend (queries, validation, time zones, point-in-polygon) and 60 backend (router, API, shadows, weather, data), and all passed on the final code. We then removed the test files to keep the final repository minimal, so what remains is lint and the type-checked production build.
What's the biggest limitation?
We model direct-sun exposure, not full thermal comfort: no air temperature, humidity or wind, uniform trees, maximum building heights, and one weather point for the campus.
What would you build next?
A comfort score with temperature and humidity, real tree sizes, door opening hours for indoor routes, live GPS navigation, and other campuses (the pipeline only needs a boundary, the OSM walk network and building heights).
Did you find any bugs while preparing?
Yes: the shadow cache could use more memory than our server has, and the campus outline didn't come back after a backend restart. Both fixed and verified, without changing any maths.

18.1 The 30-second explanation

Detour is a walking map for York's Keele Campus that keeps you out of the sun. You drop a start and an end pin, pick how much sun you want to avoid, and Detour compares the fastest route with a shadier one, telling you exactly how much extra time it costs. Behind it, we compute real building and tree shadows from the sun's position, combine them with live weather, and search every trade-off between walking time and sun exposure across the campus walkway graph.

18.2 The 90-second technical explanation

The frontend is Next.js and React with a Leaflet map. React state holds the date, time, pins and sliders; every change becomes a URL, which a custom hook debounces for 150 ms, fetches with cancellation, and validates before drawing the GeoJSON route.

The backend is FastAPI in Python. The campus is a graph of 1,804 walkway intersections and 5,172 directed edges from OpenStreetMap, projected into metres. We get the sun's elevation and azimuth from pvlib and cast shadows from 737 City of Toronto buildings and 1,181 trees with L = h / tan θ, sweeping each footprint away from the sun.

We sample every walkway every 1.5 m to get its shaded fraction, then integrate sun exposure over the walk in sun-seconds, using live direct radiation from Open-Meteo so clouds count. Instead of a single weighted cost, we run a bicriteria A* search that finds the Pareto set of routes trading time for shade. The slider picks the quickest route that removes the chosen share of the avoidable sun, and optional rain avoidance keeps you under roofs. During development, automated tests confirmed that our A* matches Dijkstra and NetworkX.

18.3 The 3-minute team presentation

0:00–0:45
Frontend person: the problem and the app

On a hot day, the fastest walk across campus is often in full sun, while a route one minute longer is in shade. Detour shows you both. [Demo: place two pins.] Green is Detour, red dotted is the fastest route. The panel says how much time and sun each takes. When I move the sun-avoidance slider, the green route changes; when I move the time, everything updates, because the app is built in React and every input is state. Changes are debounced and old requests are cancelled, so it stays responsive. Turning on Show shadows draws the actual building and tree shadows for this moment.

0:45–1:30
Graph person: the network and the search

The campus is a graph: 1,804 intersections and 5,172 directed walkway edges from OpenStreetMap, in metres. The fastest route is A*: Dijkstra guided by a straight-line lower bound, which gives the same answer while exploring about half the nodes. But for shade, a single weighted cost only finds a few routes. So we search for the Pareto set: every route where you can't get less sun without walking longer. On our demo trip that's 9 routes. The slider means "avoid this share of the avoidable sun", and we take the quickest route that does it.

1:30–2:15
Math person: sun, shadows and exposure

We compute the sun's elevation θ and azimuth α for every minute of the day. A building of height h casts a shadow L = h / tan θ long, pointing away from the sun, so at noon in June a 20 m building casts about 7 m of shadow, and in December about 48 m. We sweep each footprint along that vector. Trees are crown disks from 2 to 9 m up. Each walkway is sampled every 1.5 m to get its shaded fraction, and exposure is an integral: sun-seconds equal walking time times sun intensity times the unshaded fraction, summed edge by edge at the time you actually reach it.

2:15–3:00
Backend person: weather, engineering, honesty

Sun intensity comes from live Open-Meteo direct radiation, because shade only blocks the direct beam; on a cloudy day there is little to avoid and Detour says so. With Avoid rain on, we also count rain-seconds on unsheltered walkways and stay under roofs. It's a FastAPI backend with caching, so slider changes answer in milliseconds, and during development we checked that A* matches Dijkstra. Limits: we model direct sun, not air temperature, and trees are a standard size. Next we'd add a comfort score and live navigation. Thank you.

19If you only remember 10 things

  1. Frontend draws, backend thinks. Next.js/React/Leaflet in the browser; FastAPI/Python does all routing, sun, shadow and weather maths and returns JSON + GeoJSON.
  2. The campus is a graph G = (V, E): 1,804 nodes, 5,172 directed walkway edges from OpenStreetMap, in metres (UTM 17N). Walking speed 1.4 m/s, so τ = d / 1.4.
  3. A* = Dijkstra + straight-line lower bound (0.99 × distance ÷ 1.4). Same optimal answer, about half the nodes (876 vs 1,703).
  4. The Detour route comes from a Pareto set, not a single weight: every route that trades extra time for less sun (max 50 % extra cost, each step ≥ 2 % less sun). The slider picks the quickest that removes the chosen share of avoidable sun: target = Sfast − p (Sfast − Sshadiest).
  5. Shadow length L = h / tan θ, direction (−L sin α, −L cos α), away from the sun. Nothing below 3°, capped at 300 m. Buildings are swept footprints; trees are 3 m crowns from 2 to 9 m.
  6. Sun-seconds: Se = τ × average intensity × (1 − shade fraction). Shade fraction comes from sample points every 1.5 m and the nearest 15-minute shadow.
  7. Intensity = direct radiation / 1000 W/m² from Open-Meteo (clear-sky fallback sin θ). Clouds matter through direct radiation; cloud % is display only. Weather is cached 30 min.
  8. Units: sun avoidance 0–100 in UI and URL, ÷ 100 in the backend; sun % is already a percentage; cloud cover is 0–1. Angles in degrees, converted to radians for trig. Times are Toronto local.
  9. Coordinates: Leaflet [lat, lon], GeoJSON [lon, lat], backend (x, y) metres.
  10. Reliability: 150 ms debounce, AbortController, stale routes dimmed, Retry, validated responses; backend caches make slider moves ~15 ms. Lint and build clean; 75 tests passed before the test files were removed.
And one honest sentence

"Detour models direct-sun exposure from real shadows and live weather; it does not yet model air temperature, humidity or individual tree sizes."
